# 云端与本地开发同步

适用于 Codex、Claude、Gemini 等能读文件并运行 Git 的开发宿主。没有自动 skills 发现能力时，直接读取本文件和对应项目的交接清单；不要假称安装后能访问另一台关机的电脑。

## 先定位，再同步

读取目标项目的 AGENTS.md、STATE.json、docs/DECISIONS.md 与最新 sync/ 交接清单，只读取本轮相关源码。记录来源仓库、来源提交、目的仓库、目的目录及本地 HEAD。GitHub、Sites 源仓库、Drive ZIP 不一定同版本，按提交和校验值识别，不能只看文件名日期。

用户已要求同步时直接执行已授权同步，不重复要求确认。源码同步不等于生产发布、数据库迁移执行、EXE 更新或模型权重更新。没有发布授权时保存源码和验证结果即可。

## 云端交付

1. 先核验变更并运行相关测试/构建；记录真实命令、通过和失败、mock/真实外部接口的区别。
2. 明确文件清单。排除密钥、.env、.dev.vars、登录会话、客户/学校资料、数据库、node_modules；保留锁文件与迁移文件。已有源码中的疑似秘密先处理，扫描通过不是绝对无秘密保证。
3. 提交源码；用普通 Git 或宿主 GitHub 工具推送用户指定的仓库分支，保留未改的其他目录。默认创建 sync/<日期>-<项目> 分支，禁止 force push；合并主分支按当前授权和仓库约定执行。
4. 写 sync/<日期>.json，列来源基线、变更、验证、缺口、目标路径映射与发布状态。目标提交 SHA 写在交付回执中，避免让提交内文件自引用自身 SHA。核验远端分支 SHA 后才能说已同步 GitHub。
5. 需要离线/Drive接续时，使用 Git 原生 bundle。运行 `node scripts/transfer.mjs pack <源码仓库> <仓库外的新目录>`；它只打包已提交的 HEAD，并输出校验清单。不把完整聊天装进包。

## 本地接收

先 `git status --short`。有本地改动时保留它：优先使用独立目录或 worktree 接收，禁止 reset --hard、clean、直接解压覆盖或自动 stash。无需等待用户批准可先完成独立接收与差异检查。

有 GitHub：fetch 已核验的远端分支，核对提交 SHA，创建独立本地分支或 worktree。离线包：先核验 manifest 与 bundle SHA，再运行 `node scripts/transfer.mjs receive <现有仓库> <交接目录>`；它只导入一个新分支，不切换/合并工作区，不触碰未提交文件。

比较 merge-base 与目标差异；能快进且工作区干净时可 `git merge --ff-only <接收分支>`。历史分叉则先建集成分支、合并并解决具体冲突，保留双方修改；不要伪造快进成功。不同项目布局用显式路径映射，不合并无关历史。

按锁文件安装；不要覆盖本机密钥和私有运行目录。对照交接清单执行测试、构建。数据库只应用未执行的正向迁移，先保留可恢复副本；更新桌面程序须实际重建相应平台安装包。云端 React 源码更新不能宣称 Windows EXE 已更新。

## 多模型交接回执

返回：来源与目标提交、接收分支/路径、变更内容、验证结果、待完成项、是否部署。另一个聊天不会自动收到本对话消息：把 [接续指令](START_HERE.txt) 与交接清单发给它，或放到已有项目入口和技能索引；不宣称已通知不可访问的聊天。

实现同步难题前先检索官方文档/已有代码，优先复用 Git 自带能力，避免为同步新增模型调用。参考：[Git bundle](https://git-scm.com/docs/git-bundle)、[Git worktree](https://git-scm.com/docs/git-worktree)。

## Coursework 自动同步入口

每次经过验证并提交的云端更新，运行 `python scripts/sync-github.py --mirror <干净的GitHub工作树> --branch <该工作树当前sync分支> --receipt <仓库外回执路径>`。该入口仅打包已提交源码，映射到 GitHub 的 `cloud/`，保留桌面代码，不强推、不携带学校会话、不新增模型调用。推送后核对远端 SHA；权限不足时退出码为 2，保留本地提交并将回执记为 pending。修复 GitHub 授权后重新运行即可。不能将 pending 回执说成已经同步成功。
